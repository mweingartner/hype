# Turtle Graphics for HypeTalk

## Purpose

HypeTalk had no way to script vector drawings onto a card: the raster `drag`
paint path is pixels-only and permanent once painted, and shape parts could
only be placed one at a time by hand. Turtle graphics gives stack authors and
the AI assistant the classic Logo turtle — an imperative pen steered with
`forward`/`right` — whose trail becomes real, editable shape parts.

## Value

Stack authors get a Logo turtle whose commands (`forward`, `right`,
`beginFill`/`endFill`, `circle`, `repeat`, …) read like the language they
already know, and whose output is not a picture but ordinary `.freeform`/
`.oval` parts — selectable, movable, scriptable, and saved in the `.hype`
document like anything drawn by hand. The AI assistant gets the identical
vocabulary through one tool, `draw_with_turtle`, so a script generated by the
AI and a script typed by a person are indistinguishable in behavior and
output — the two surfaces stay equivalent by construction, not by parallel
maintenance.

## Scope

**Covers:**
- The turtle vocabulary (movement, rotation, pen, fill, drawing primitives,
  canvas/reset commands) and the `the <prop> of the turtle` property surface.
- The vector output contract: every flush emits an ordinary `.freeform` or
  `.oval` shape part named `turtle path/fill/dot N`.
- A single engine (`TurtleEngine`, in HypeCore) behind both the HypeTalk
  interpreter and the `draw_with_turtle` AI tool — one geometry
  implementation, one set of error strings, used by both front-ends.
- A 16-name classic color table added to the shared `HexColor` validator
  (`red`, `blue`, `orange`, …), available to every color-kind property on
  every surface, not just the turtle's.
- Alignment of the `.freeform` renderer contract across all three render
  sites (editor CG, editor SpriteKit, and the deployed/exported runtime) so
  an open (unfilled) trail and a closed fill render the same way everywhere.
- The `draw_with_turtle` AI tool: an authoring-only tool that parses a
  turtle-only program with the real HypeTalk parser and executes it through
  the same engine.

**Does not cover, by design:**
- No document-format change: no new `PartType`, no `PathPoint` change, no
  `.hype` coding-key additions, no `documentVersion` bump. Turtle drawings
  are just parts.
- No visible turtle cursor and no raster "paint mode" — deferred; a turtle
  setting could later route through the existing `DrawingProvider`, but v1
  ships neither.
- `draw_with_turtle` is authoring-catalog-only. It is **absent from
  `RuntimeAIToolCatalog`** — the deployed-app runtime AI surface cannot draw
  with the turtle, only the authoring assistant can.
- The tool's program allowlist is **all-or-nothing**: it accepts only
  turtle verbs, turtle property sets, `reset turtle`, `--` comments, and
  `repeat N times` / `repeat with i = a to b` loops whose count/bound/value
  expressions are arithmetic-only (literals, variables, `+ − * / mod div ^`,
  unary negate, and `of the turtle` property reads). A `functionCall` in
  **any** expression position — not just top-level statements — refuses the
  entire program with zero mutation; this closes the path where
  `repeat foo() times` or `set the heading of the turtle to foo()` could
  otherwise smuggle an arbitrary user handler past the sandbox.
- The tool's `ExecutionContext` is built with deny-by-default stub providers
  only (no real file, host, or runtime provider). Even if a stack-local
  `on forward` handler shadows a turtle verb (dispatch precedence is
  unchanged by this feature), its blast radius through this tool is document
  mutation only — never the filesystem, network, host shell, or runtime.
- Per-run DoS bounds are enforced by the engine (at most 200 emitted parts
  and 50,000 total path points, error E8) and, independently, by the
  interpreter's existing `instructionLimit` guard, which this change extends
  to the `repeat N times` / `repeat with` loop heads so an empty-body loop
  with a huge count (e.g. `repeat 1000000000 times`) cannot spin unbounded
  or uncancellably — it now terminates with "Instruction limit exceeded"
  like every other loop shape. The parser also refuses a program nested more
  than 200 levels deep before it ever reaches the recursive-descent parser.
- Turtle session state (position, heading, pen state, fill state) lives only
  in `document.scriptGlobals["__turtle"]`. It is deliberately excluded from
  `.hype` file coding — closing and reopening a stack resets the turtle to
  defaults, and nothing turtle-related is ever persisted to disk.

## Functional details

### Vocabulary

All commands are case-insensitive; numeric arguments are ordinary HypeTalk
expressions coerced the same way every numeric argument in HypeTalk is
(`Double(_:) ?? 0`, so garbage coerces to 0, not an error); color arguments
accept `#RRGGBB`, `#RRGGBBAA`, or a classic color name.

| Group | Commands |
|---|---|
| Movement | `forward n` / `fd n`, `back n` / `bk n` |
| Rotation | `right deg` / `rt deg`, `left deg` / `lt deg`, `setHeading deg` / `setH deg` |
| Position | `setPos x, y` / `setXY x, y`, `home` |
| Pen | `penUp` / `pu`, `penDown` / `pd`, `setPenColor c`, `setPenWidth w` / `setPenSize w` |
| Fill | `setFillColor c`, `beginFill`, `endFill` |
| Primitives (turtle does not move) | `circle r`, `arc deg, r`, `dot` / `dot d` |
| Canvas / reset | `clean`, `clearScreen` / `cs`, `reset turtle` |

All of this parses without new reserved lexer keywords — it rides the
existing external-command path, so a user-defined handler named `forward`
(or any other turtle verb) keeps message-dispatch precedence over the
built-in, identically on both surfaces.

### Conventions

- **Heading:** degrees, 0 = up (toward the card top), clockwise positive,
  normalized to `[0, 360)`.
- **Coordinates:** card coordinates — top-left origin, y-down, points — the
  same system as `the loc`, `drag`, and `the mouseLoc`.
- **Home:** the card center, `(stack.width/2, stack.height/2)`.
- **Movement math:** `dx = n·sin(h°)`, `dy = −n·cos(h°)`, with exact table
  values at the cardinal headings (0/90/180/270) so a `repeat 4 times /
  forward n / right 90 / end repeat` square closes exactly (first vertex ==
  last vertex), not approximately.
- **Defaults:** pen down, `penColor "#000000"`, `penWidth 2`,
  `fillColor "#000000"`, not filling, at home with heading 0.
- **Positions clamp defensively** to ±1,000,000; the turtle may otherwise
  leave the card and come back, like any part.

### Property surface

`the <prop> of the turtle` reads and (where noted) writes:

| Property | Aliases | Get | Set |
|---|---|---|---|
| `position` | `loc`, `location` | `"x,y"` | yes — like `setPos` |
| `xcor` / `ycor` | — | number | read-only (use `setPos`) |
| `heading` | — | 0–359.999… | yes ≡ `setHeading` |
| `penDown` | — | `true`/`false` | yes ≡ `penDown`/`penUp` |
| `penColor` | — | `#RRGGBB[AA]` | yes ≡ `setPenColor` |
| `penWidth` | — | number | yes ≡ `setPenWidth` |
| `fillColor` | — | `#RRGGBB[AA]` | yes ≡ `setFillColor` |
| `filling` | — | `true`/`false` | read-only |

Aliases are symmetric between GET and SET. Setting a read-only property
(`xcor`, `ycor`, `filling`) or an unknown property errors in the shared
registry copy style (lowercase start, quoted name, em-dash guidance):

```
"xcor" of the turtle is read-only — set the position instead.
"filling" of the turtle is read-only — use beginFill and endFill.
no such property "wobble" for the turtle — the turtle has position, xcor, ycor, heading, penDown, penColor, penWidth, fillColor, and filling.
```

### Output contract

Every flush of the turtle's stroke or fill accumulator emits one ordinary
`Part`:

- `partType .shape`; `shapeType .freeform` (strokes and fills) or `.oval`
  (dots).
- `pathData` is absolute card-coordinate vertices, unrounded doubles, in
  draw order.
- A **stroke** part has `fillColor ""` (the app-wide "auto/none" sentinel —
  it is explicitly open and unfilled, not "white" or "default"),
  `strokeColor` = pen color, `strokeWidth` = pen width.
- A **fill** part has `fillColor` = the turtle's fill color, and an outline
  taken from pen state at `endFill` (pen down → `strokeColor`/`strokeWidth`
  from the pen; pen up → `strokeWidth 0`).
- The frame is the tight bounding box of `pathData`, padded by
  `strokeWidth/2` per side (minimum 1×1).
- The name is `turtle path N` / `turtle fill N` / `turtle dot N`, where `N`
  is the smallest positive integer not already used with that prefix on the
  target card — so drawing repeatedly never collides with a prior drawing's
  name.

**Flush lifecycle:** the active stroke accumulator opens at the first
pen-down movement and flushes on `penUp`, on a pen color/width *change*, on
`beginFill`, on `clean`/`clearScreen`/`reset turtle` (which discard rather
than emit), on card navigation, and at the end of the top-level run — which
is what makes the message box a live REPL: type `forward 100`, see the part
appear immediately. An unclosed `beginFill` at end of run emits nothing and
sets `the result` to the E7 text below, rather than raising a script error.

### Named colors

`HexColor.normalized` accepts 16 classic names, case-insensitively, in
addition to `#RRGGBB`/`#RRGGBBAA` hex and the `""` auto sentinel — usable
anywhere a color property is set, not just by the turtle:

| Name | Hex | Name | Hex |
|---|---|---|---|
| black | `#000000` | cyan | `#00FFFF` |
| white | `#FFFFFF` | magenta | `#FF00FF` |
| red | `#FF0000` | lime | `#00FF00` |
| green | `#008000` | navy | `#000080` |
| blue | `#0000FF` | teal | `#008080` |
| yellow | `#FFFF00` | gray / grey | `#808080` |
| orange | `#FFA500` | brown | `#A52A2A` |
| purple | `#800080` | pink | `#FFC0CB` |

### Renderer contract

All three places `.freeform` parts render — the editor's CG renderer
(`ShapeRenderer`), the editor's SpriteKit renderer (`ShapePartNode`), and the
deployed/exported runtime (`TargetRuntimeShapeView`) — share one open/closed
decision through `RenderGeometry.freeformIsOpenStroke`: `fillColor == ""`
renders as an **open**, stroked, round-capped/joined polyline (no close, no
fill); a non-empty `fillColor` renders **closed**, filled, and stroked (when
`strokeWidth > 0`). This closed a real defect: the exported/deployed runtime
previously rendered a `fillColor ""` freeform as a solid **black** filled
polygon (because `Color(hex: "")` resolves to opaque black), so an
unfilled turtle stroke would have shipped looking like a black blob in any
exported stack. Existing freeform parts (default `fillColor "#FFFFFF"`)
still render closed and filled everywhere — unaffected.

### Error handling

Every turtle error string is owned by `TurtleEngine.ErrorCopy` and is
byte-identical whether it surfaces as a HypeTalk `ScriptError` message or as
the `draw_with_turtle` tool's result text:

| Code | Message |
|---|---|
| E1 | `turtle: "blurple" isn't a color — use #RRGGBB, #RRGGBBAA, or a name like red, blue, orange.` |
| E2 | `turtle: circle needs a radius greater than 0 (got -5).` (same shape for `arc` and `dot`) |
| E4 | `turtle: already filling — call endFill before starting another fill.` |
| E5 | `turtle: endFill without beginFill — nothing to fill.` |
| E6 | `turtle: fill needs at least 3 points — nothing drawn.` (via `the result`, not a script error) |
| E7 | `turtle: beginFill was never closed — no fill drawn.` (via `the result`) |
| E8 | `turtle: drawing limit reached — a single run may draw at most 200 shapes and 50000 points.` |
| E9 | `turtle: line 4 isn't a turtle command ("go next card") — draw_with_turtle accepts only turtle commands and repeat loops.` (`draw_with_turtle` only) |

E6 and E7 are not script errors — they are quiet: nothing is drawn and `the
result` carries the explanation, matching HyperCard's "success is silent,
failure explains itself" voice. On the HypeTalk surface, E1/E2/E4/E5/E8 stop
the run but leave whatever the run already flushed in place (the live
publish channel already applied it); on the `draw_with_turtle` surface every
engine error is all-or-nothing — the document is untouched on failure.

## Usage

**A minimal handler:**

```
on mouseUp
  forward 100
end mouseUp
```

Draws one `.freeform` part named `turtle path 1` from the card center
straight up 100 points, `strokeColor "#000000"`, `strokeWidth 2`,
`fillColor ""`.

**A filled shape:**

```
on mouseUp
  setPenColor "black"
  setFillColor "orange"
  beginFill
  repeat 3 times
    forward 130
    right 120
  end repeat
  endFill
end mouseUp
```

Emits exactly one `.freeform` part — `fillColor "#FFA500"`, outlined in
black — not three separate strokes; movement inside a fill span feeds only
the fill polygon.

**A repeat-loop pattern** (from the Turtle Garden example — a square, then a
twelve-circle flower):

```
on mouseUp
  reset turtle
  clearScreen

  setPenColor "blue"
  setPenWidth 3
  penUp
  setPos 200, 380
  penDown
  repeat 4 times
    forward 120
    right 90
  end repeat

  penUp
  home
  setPenColor "purple"
  repeat 12 times
    forward 45
    penDown
    circle 22
    penUp
    back 45
    right 30
  end repeat
end mouseUp
```

The square is one part with 5 vertices (first == last); each of the 12
circles is its own `turtle path N` part (`circle` never moves the turtle,
so pen-up travel between petals draws nothing).

**Reading and setting a turtle property:**

```
put the heading of the turtle into currentHeading
set the heading of the turtle to 45      -- identical to `setHeading 45`
put the position of the turtle into field "coords"   -- "x,y"
```

**The `draw_with_turtle` AI tool** (authoring only), given the program body:

```
setPenColor "blue"
repeat 4 times
  forward 100
  right 90
end repeat
```

returns:

```
Drew 1 shapes on card "Garden": turtle path 1 (5 points). Turtle at 400,300 heading 0, pen down.
```

**A refusal** — a non-turtle line inside a `draw_with_turtle` program:

```
forward 100
go next card
```

refuses with

```
turtle: line 2 isn't a turtle command ("go next card") — draw_with_turtle accepts only turtle commands and repeat loops.
```

and creates **zero** parts — no partial drawing, because the whole program
is validated against the turtle-only allowlist before any statement
executes.
